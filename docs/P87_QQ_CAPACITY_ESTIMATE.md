# P8.7 QQ 容量与成本离线测算

日期：2026-11-03。**以下是配置化假设与算术结果，不是 DeepSeek 报价、实际账单、QQ 可用配额或服务器实测容量。** 真实模型请求、QQ 连接与付款均为 0，供应商实际费用字段保持 `null`。

## 1. 可复算的假设

配置：`backend/app/modules/qq_p87/capacity_example.json`；计算器：`backend/scripts/p87_capacity_estimate.py`。从项目 `backend` 目录可离线执行：

```powershell
.\.venv\Scripts\python.exe -B -m scripts.p87_capacity_estimate
```

这些配置只含公开示例参数，不能填凭证。计算器拒绝未知字段，不会将额外凭证字段复制到输出。

| 参数 | 示例值 | 含义与限制 |
| --- | --- | --- |
| 普通输入价 | USD 1.00 / 百万 Token | 刻意使用的虚构价格，不代表任何供应商现价 |
| 缓存命中输入价 | USD 0.10 / 百万 Token | 缓存命中是单独假设；不保证有命中 |
| 输出价 | USD 2.00 / 百万 Token | 虚构价格 |
| 每消息输入 / 输出 | 2,000 / 300 Token | 包含人格、授权记忆和当前消息的总输入预算假设 |
| 输入中缓存命中部分 | 500 Token | 属于 2,000 输入，不可重复计入 |
| 单次最大输入 / 输出 | 8,000 / 800 Token | 保守预留不假定缓存命中 |
| 日活率 / 活跃时段 | 注册用户的 100% / 每天 8 小时 | 用于压力规划，实际留存和日活尚未知 |

典型每条成本：`(2000−500)×1/1e6 + 500×0.1/1e6 + 300×2/1e6 = USD 0.00215`。无缓存时为 USD 0.00260；最大预算为 `8000×1/1e6 + 800×2/1e6 = USD 0.00960`。内部计算使用整数微美元向上取整，避免浮点低估。

## 3. 并发、排队与失败

公式：活跃时段均值 `λ=D/(8×3600)`；峰值 `λp=10λ`；规划并发 `C=ceil(λp×5/0.7)`。

计算器另模拟“空系统一次收到约 10 秒峰值流量”：`B=ceil(10λp)`，最后一项开始等待 `max(ceil(B/C)−1,0)×5秒`，当前九组均为 5 秒。**这只是一批独立突发的算术，不能当作持续随机到达下的 P95/P99 排队时间。** 需要实际服务时间分布与沙箱压测后才能给出体验承诺。

未来服务建议有界队列、账号单在途、bot/平台总并发和明确超时，例如在确认条件后配置约 `2C` 的等待上限、模型 20 秒服务截止和更短于被动回复有效期的总截止。仅在每个作业都满足 20 秒上限时，`2C` 队列的容量等待上界才约为 40 秒；网络异常、限流和外部排队会改变体验。超过队列或预算立即拒绝，不能无限等待再连续付费重试。

本地实验使用更小的参数：2 个并发、32 个待处理、2 秒模型和队列超时、1 秒发送超时、120 秒回复期限。这些验证保护语义，不代表生产性能调优。模型已开始但超时、费用不明时保留最坏预算，实际费用仍为 `null`；明确没开始的任务释放。QQ 发送回执不明不自动重发，也不重复扣除同一消息的额度。

[DeepSeek 现网并发文档](https://api-docs.deepseek.com/quick_start/rate_limit/)在本次核查时列出 `deepseek-flash` 2,500、`deepseek-v4-pro` 500 的账号级并发，同账号多个 Key 共享限制；超限可能 429。实际账号许可、可用容量、Token 吞吐、延迟、模型名称和错误行为均未实测，不能用文档上限当本项目吞吐承诺，更不能换 Key 绕过限制。该页还说明上游可能长时间保活，服务自身仍应设置更短截止。

官方页另有 `user_id` 隔离缓存/调度的说明。未来接真实模型应评估以不可逆、非个人信息的 owner/pet 域标识使用；本轮没有修改现有 DeepSeek Provider，也没有验证该参数的真实效果。

## 5. QQ 连接与官方权限

模式 A 的连接数主要随 bot/分片数变化，不随用户数线性增加。本算例暂假设 4 个官方 bot 连接，**不代表已创建、获批或确实需要 4 个 bot**；Webhook 模式可能不需要常驻 WebSocket，但增加公开 HTTPS、验签、重放和可靠队列成本。

模式 B 按每用户 1 个已获准官方 bot、每连接假设 0.75 MiB，100/500/1,000 人约为 100/500/1,000 个连接及 75/375/750 MiB 连接内存，未包含 worker 基础占用。这是需要实测的占位参数，不能每用户另启 Electron/OpenClaw 进程。Access Token 按 AppID 共享缓存、单飞刷新和错峰重连；不共享不同 AppID 的 OpenID。平台不能批量创建相似 bot 来绕过账号名额与审核。

[单聊发送文档](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_users_user_openid_messages.post.html)列出接口 100 QPS，主动消息还有另外限制；这些不是申请本项目容量的批准。保守原型只对授权 C2C 入站回一条，不主动推送；文档的 60 分钟/5 分钟差异、可服务对象数、内容审核与返回状态必须真实沙箱确认。高场景约 17.36 条/秒也不能由此推断在一个 bot 下已获准服务。

## 6. 用量流水与后续验证

原型账本记录 owner UUID、pet UUID、bot ID、通道名、HMAC 身份/消息键、会话 UUID、模型名、模拟输入/输出/缓存计数、模拟预算、内部额度单位、请求状态和尝试次数；`actual_cost_usd=null`、`simulated=1`。Mock 模型的计数实际采用 UTF-8 字节作为确定性实验单位，**不是 DeepSeek Tokenizer**；不得用演示中的数字推算真实账单。

下一阶段先在获得官方许可的沙箱接固定 Mock，测验签、重复投递、真实回执、限流、重连、队列截止与资源。取得另行授权后才能以严格预算测真实模型 Token/延迟/账单。当前九组结果是规划输入，不证明已支持 100～1,000 名真实用户。
