# 免费额度系统后端评估（设计，未实施）

本轮没有新增迁移、改动共享数据库、配置真实支付或发起真实模型请求。

## 现状

`app/modules/wallet/models.py` 已有钱包、预留、用量和账本表，但 WalletService 仍为 Protocol，`POST /wallet/reservations` 明确返回未实现。数据库约束不等于已经具备原子预留、结算和退款能力。

当前 chat_runner 的用户/会话/生成锁、幂等与取消屏障可复用；P8.1 LiveBudget 是验收进程内的请求上限，不是多实例生产额度系统。Redis限流也不是可靠的长期额度账本。

## 最小后端工作

1. 使用独立的免费配额授予、预留和不可变用量账本，先以整数请求数及输入/输出Token上限表达额度，不把免费次数包装成充值余额。旧钱包结构保持兼容，不直接启用空实现或客户端传入金额。
2. 账户级日/月额度是预算主体，宠物和generation仅作为隔离归属；跨宠物共享同一账户额度不能导致共享聊天或记忆。增加全局日开销上限、单请求输入/输出上限、模型白名单、邀请有效期及总开关。
3. 在接收生成时原子预留，在最终上游派发前复核当前授权、隐私epoch、provider/model和额度；请求路径不能接受前端自行选择付费provider、额度或价格。
4. 预留与生成绑定唯一generation，幂等键相同只返回原结果，参数不同拒绝；并发进程通过PostgreSQL行锁与唯一约束协调，不能只依赖进程内asyncio.Lock。
5. 与既有锁顺序一致：用户 → 配额/预留 → 会话 → 生成，终态结算也遵守同序。只在单次事务提交后派发，超时、崩溃和重放不能重复占额或结算。
6. 尚未准入上游的拒绝可释放完整预留；已派发失败或取消且usage未知时先挂起对账，不能直接承诺退款/免费。P8.1真实取消费用仍未验证，必须按可能产生用量处理。
7. 可靠usage回来后，用固定的计价版本及整数计量结算，不能超出预留硬上限；缺失usage采用保守上限并标记待核对。不得把估算美元当成实际账单。
8. Mock宠物不扣真实模型额度；问候仍为本地零Token内容。模型网络/额度失败不自动切换其他供应商或重新生成。

## 接口与文件边界

未来迁移版本需在实际开发时根据当时head分配，本轮不预占迁移号。预计新增 quota 模块与隔离迁移/测试，定向接入 companion 接收事务、runner dispatch guard及终态提交；不重构人格、记忆授权或历史API。

新增只读额度接口返回 remaining/reset_at/状态，不返回密钥、用户账本明细或其他宠物内容。额度不可用时停止新真实生成并给出明确状态，历史读取仍可用。管理授予额度需要独立管理员权限，不能开放“客户端领取任意次数”。

内测邀请需服务器签发、有限次数/期限、只保存令牌哈希，辅以账户/IP速率限制；不收集聊天正文以判定额度，不把记忆授权与领取额度绑定。

## 必要验证与上线条件

离线测试先覆盖数学上限、幂等冲突、Mock不扣额、准入前释放、准入后未知usage挂起、取消/完成两种竞态、重复终态及崩溃补偿。随后在新建且身份绑定的隔离PostgreSQL中验证并发耗尽、锁顺序和重启恢复，禁止复用共享库做破坏性测试。

只有配额与总开关在多个后端进程上都能硬性限额、数据隔离通过、服务端持有密钥且用户看到真实发送/成本边界后，才适合给10–30人发放真实免费额度。当前仍为设计，不能宣传免费额度已提供，也不接入支付、充值或自动扣款。
