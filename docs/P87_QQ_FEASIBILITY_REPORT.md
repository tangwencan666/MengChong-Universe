# P8.7 QQ AI 宠物可行性报告

核查日期：2026-11-03。结论：**官方接入技术上可行，优先设计模式A的受控单聊；当前不能承诺面向公众上线、商业托管或一人一个独立QQ机器人。** 本轮只研究和运行本地Mock，不登录QQ、不创建机器人、不发送真实消息、不调用付费模型。

本报告先于原型实现写入。原型及测试结果完成后另在文末补充，未验证能力不标为通过。

## 1. 官方支持与证据分级

| 能力 | 本次核查结果 | 依据与边界 |
| --- | --- | --- |
| QQ单聊、群聊、频道 | 官方文档明确支持 | [现网接入指南](https://bot.q.qq.com/wiki/)、[消息概述](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html)；实际账号权限仍需核对 |
| HTTPS OpenAPI、WebSocket、Webhook | 文档均有支持 | [事件订阅](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/interface-framework/event-emit.html)；Webhook要求HTTPS、验签；本轮未连真实网关 |
| 官方Python参考SDK | 有botpy链接 | [启动接入](https://bot.q.qq.com/wiki/develop/api-v2/)；不必为此引入完整OpenClaw执行环境 |
| Tencent Connect QQBot插件 | 参考仓库支持C2C、群聊、多机器人、两种传输 | [官方组织仓库](https://github.com/tencent-connect/openclaw-qqbot)、[中文README](https://github.com/tencent-connect/openclaw-qqbot/blob/main/README.zh.md)；技术实现和MIT许可不等于获得QQ平台运营许可 |
| 官方扫码配置 | 插件README和`src/setup/login.ts`有官方connector扫码路径 | 支持该工具自己的流程；未确认萌宠溜达作为第三方SaaS可复用其授权、收取或托管凭证。没有执行CLI，也没有扫码 |
| 每用户不同QQ机器人身份 | 只有分别创建的官方机器人才能形成不同外部机器人身份 | 多宠物实例ID不会自动成为多个QQ账号；统一入口的QQ名称/头像由机器人公共资料决定，不能承诺按用户变化 |
| 大量普通用户 | 有条件可行，不是当前已获准 | 应走经认证/允许公开服务的主体和服务范围，取得需要的审批、隐私和运营确认，再压测 |

当前实现选择**直接官方协议的可替换Adapter边界**；不安装或运行QQBot/OpenClaw插件，不使用非官方个人QQ协议，不登录个人QQ号。

## 2. 个人、企业与公开服务

[现网指南](https://bot.q.qq.com/wiki/#_3-创建机器人)说明个人认证可创建5个机器人；企业认证账号通常10个，同企业主体总上限50个。服务范围说明个人认证暂不支持公开使用（历史已审核公开服务有例外），企业认证可设置公开服务范围，个人进群上限另有规定。这些数值是核查时文档描述，不能代替本项目账号控制台的实际许可。

官方GitHub旧版`bot-docs/docs/README.md`仍有“个人仅频道、群/单聊不开放”的旧表，与现网新版范围描述不同；不能照抄旧表，也不能由新API的存在推断所有个人账号已获所有权限。以现网、账号控制台和官方书面答复共同确认。[官方文档仓库](https://github.com/tencent-connect/bot-docs)

**不能通过批量创建相似机器人来给1000名用户分配1000个QQ身份。** 现网[运营规范](https://bot.q.qq.com/wiki/business/)限制批量注册/重复提交大量相似机器人，并对付费添加、依赖其他应用、集中推荐跳转、数据使用和未成年人保护提出要求。真实上线前须确认以下方案的具体适用范围。

## 3. 两种模式比较

| 维度 | A：平台统一官方机器人 | B：用户自己的官方机器人 |
| --- | --- | --- |
| 普通用户体验 | 优先：添加获准机器人，选择宠物；不填模型密钥 | 需要用户完成官方创建/主体和服务范围流程；平台可解释步骤，不能假装免审核自动创建 |
| 身份 | 一个公共QQ入口，内部按owner + pet instance隔离 | 每个官方bot有独立AppID和外部资料；内部仍按owner + pet instance隔离 |
| 多宠物 | 同入口内切换当前宠物；不改变其他用户的当前宠物 | 可一bot多实例，或按用户已拥有的bot配置；不擅自批量建号 |
| 账号绑定 | QQ已验证入站身份与平台账号双向确认；可撤销 | 除用户身份外，还需验证用户有权管理该bot，不能只凭输入AppID认领 |
| 凭证 | 少量平台bot凭证保管与轮换 | 每租户凭证加密、隔离、轮换、撤销，负担和泄露面更大 |
| 技术/成本 | 少量连接或Webhook统一接收，集中路由、预算、风控 | 多bot长连接/Token刷新/权限差异更复杂，不能每用户启动一个OpenClaw/Electron进程 |
| 平台授权 | 需确认服务主体、统一多人入口、外部账号关联和AI服务运营 | 另需确认第三方配置/托管凭证、委托授权、机器人转移/撤销的允许方式 |
| 本轮建议 | 本地Mock主路径，未来首个真实沙箱候选 | 保留为高级模式设计，真实凭证接入保持关闭 |

普通用户在模式A下**不需要自行创建机器人**；这不等于平台已经取得公开托管许可。模式B下用户需要拥有经官方流程创建且有权委托管理的机器人。技术上一个服务可管理多个bot，平台政策上的代配置/多租户托管仍待官方确认。

## 4. 当前可验证的消息、身份和凭证规则

- 入站单聊事件是`C2C_MESSAGE_CREATE`，群聊有`GROUP_AT_MESSAGE_CREATE`，开启全量模式后另有`GROUP_MESSAGE_CREATE`；不能把群成员消息当作私聊。第一阶段只处理明确授权的C2C纯文本，不读取群私有记忆。[单聊事件](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/c2c_message_create.html)、[群全量事件](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_message_create.html)
- OpenID按AppID分域；群、成员、单聊标识也有差别。虽然部分新事件列出可为空的union字段，本轮不依赖跨AppID合并，不按QQ号码或昵称绑定。[API调用指南](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/api-call-guide.html)
- AppID不是用户身份凭证，AppSecret和Access Token仅供后端；Token旧鉴权已经弃用。现网访问凭证页给出最长约7200秒有效期及刷新窗口，还提醒取Token失败可能HTTP200但响应体含错误code。不得只检查HTTP状态。[访问凭证](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/access-token.html)
- Webhook必须验证原始请求体签名、时间、新鲜度、bot路由和事件去重；实际QQ为Ed25519规则。Mock的实验HMAC不是QQ验签实现。[官方安全与授权](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/interface-framework/sign.html)
- 单聊发送页说明被动回复60分钟、每条最多4次，但同页`msg_id`参数仍写5分钟，存在文档内差异，必须沙箱核验；本地策略取更短120秒，最多一条完整回复、不主动推送、不靠递增序号重复补发。[发送单聊消息](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_users_user_openid_messages.post.html)
- 现网单聊发送页列接口100QPS（所有消息类型），另有主动消息按bot/关系/认证类型的限制；群/频道限制不同。不能将主动消息配额当作被动回复配额。实际配额、内容长度、审核异步状态和拒收行为仍须控制台及沙箱验证。

## 5. 产品流程与授权限制

未来用户体验：选择宠物 → 选择QQ连接方式 → 按官方允许流程确认身份/授权 → 在QQ聊天。保留“暂不连接，直接桌面陪伴”。模型密钥完全在服务端，用户不填DeepSeek Key，不看Webhook/Python/Docker配置。

模式A的基础服务宜支持QQ内原生入门：验证QQ入站后，取得用户同意，建立平台内部匿名化身份和宠物实例。关联现有网页/桌面账号及授权旧记忆应是明确、可撤销的额外操作。**不得未经确认强制安装萌宠溜达或使用其他应用才能使用QQ基础功能**，避免与运营规范冲突。网页绑定的双向证明流程本轮仅作为已登录用户的本地实验，不代表真实用户流程已获平台授权。

模式B应展示真实官方创建/扫码步骤和权限状态；无法确认时显示“待官方授权验证”，不能显示假二维码或“已连接”。一个普通用户如想要专属QQ机器人名称/头像，必须明确它不同于内部宠物名字，不能通过宠物重命名实现。

## 9. 本地原型交付与验证

最终本地阶段状态：`P87_FEASIBILITY_AND_LOCAL_MOCK_VERIFIED`。这不是QQ真实接入或公开运营验收通过。

原型实现：固定Mock消息签名 → 双向绑定证明 → owner/pet UUID校验 → 事务去重、三层预算和频控 → 现有人格/授权记忆只读接口 → Mock候选 → 保守内容检查 → 再鉴权、固定收件人回发 → 最小用量流水。无公开路由，无真实QQ/模型实现，无新依赖、迁移或原应用代码修改。

已通过的关键离线场景包括：重复消息并发只生成/发送一次；同名同种宠物和跨账号记忆隔离；bot分域身份；错误宠物/非法用户/过期或篡改事件拒绝；双向口令到期、猜测次数和冒领防护；额度及三个预算/速率层级；候选不能指定收件人；已知注入/诈骗样例拒绝；模型超时不重跑；发送回执不明不重发；明确没发出时只重投同一候选一次；解绑/暂停/记忆撤销阻止旧候选；关闭释放任务和内存捕获记录；重启不重跑在途消息。
